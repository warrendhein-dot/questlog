# Threat model (v0.7, Phase 1 slice 7)

A threat model answers four questions: what are we protecting, who or what could attack it, how, and what stops them. We write it **before** the risky features exist and revisit it at each phase.

## 1. What we protect (assets)

| Asset                                   | Why it matters                                    | Exists from |
| --------------------------------------- | ------------------------------------------------- | ----------- |
| Task data (titles, notes, dates, steps) | Personal, may contain sensitive detail            | Phase 1     |
| Google / Microsoft OAuth refresh tokens | Grant ongoing read access to email and calendar   | Phase 4     |
| Email and calendar content              | Highly sensitive; passes through to the AI        | Phase 4     |
| Anthropic API key                       | Spend money; could be abused                      | Phase 3     |
| Session / login                         | Controls access to all of the above               | Phase 1     |
| Integrity of XP and progress            | Low stakes, but "cheating" undermines the product | Phase 2     |

## 2. Who might attack (actors)

- **Opportunistic internet attacker**: scans for common web flaws, leaked keys, outdated libraries.
- **Malicious email or calendar sender**: anyone can send you an email or invite. Their text reaches our AI. **This is the most important actor for this product.**
- **Supply-chain attacker**: a compromised npm package or GitHub Action.
- **Ourselves**: accidentally committing a key, over-broad permissions, a misconfigured database.

## 4. Accepted risks

**A1: Dev-tooling advisory (`braces` / `micromatch` / `fast-glob` via `eslint-config-next`).** `npm audit` reports 5 high-severity findings, all one chain: a denial-of-service bug in a glob-matching library used only by the linter, on our own source files. It never ships to users and processes no untrusted input. The suggested "fix" is a _downgrade_ of `eslint-config-next` to a version incompatible with Next 16. CI blocks on production-dependency findings only and shows the full audit as informational. **Revisit** when `eslint-config-next` publishes an update, or at each phase boundary.

**A2: The allow-list only guards account _creation_.** Removing an address from `allowed_emails` later does not sign out or delete a user who already exists. To revoke someone, delete them in Supabase (Authentication > Users). With a single owner this is acceptable. **Revisit** if the app ever gains a second user.

**A3: Sessions are validated by Supabase on each request.** That costs one network round trip per page load, which is fine for one user and gives immediate revocation. If latency matters later, `getClaims()` verifies the token locally but accepts a revoked session until it expires.

**A4 (resolved in slice 6): Completion time was written by the app and the database let the owner set it.** Completing and re-opening now go through `complete_task` / `reopen_task`, which stamp the time with the database's clock, and the API's update permission on `completed_at` is revoked (tested). The description below is kept for the record. Still to do in Phase 2: compute XP from this time, with the daily cap and minimum task age (threat 15).

_Original text:_ **Completion time is written by the app and the database lets the owner set it.** `completed_at` is set from the app server's clock, and the owner can also write any value through the API. That is harmless for a to-do list, but it means completion times cannot be trusted for XP. **Fix in Phase 2** (before any XP exists): move completion into a database function or trigger that stamps the time itself, and compute XP from that, with the daily cap and minimum task age (threat 15).
